## Implementation summary and decisions

Request cancellation now follows the existing one-request/one-job relationship through the shared API, restricted preload, validated main-process IPC and worker dispatch. Both cancellation endpoints return the current snapshot. Queued cancellation is terminal without source attempts; running cancellation persists intent immediately and settles active work before its terminal state. Completed outcomes remain unchanged.

Cancellation records `USER_CANCELLED`. Atomic SQLite JSON updates retain durable cancellation intent and reasons when execution saves an older in-memory job. A cancellation fence after synchronous adapter normalization prevents that boundary from erasing cancellation and committing a new observation. Existing transactions retain previously committed listings, counts and candidate progress. No schema migration or dependency is needed.

No approved deviations. The local worker API seam with temporary SQLite databases and deterministic adapters is explicitly confirmed by #17. Shared-work cancellation remains #6's responsibility. An active adapter that ignores its abort signal must settle before running cancellation becomes terminal. No forced termination or new timeout policy is introduced.
