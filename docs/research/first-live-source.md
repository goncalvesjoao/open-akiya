# First live source investigation: Tsubata Town open-data CSV

Reviewed 15 October 2026 (Asia/Tokyo). Research only; no adapter enabled, pilot completed, issue closed, or implementation tickets created. Read alongside [the live-source spec](../specs/live-area-source-integration.md), [implementation plan](../implementation-plan.md), [background research](../nightly-listing-ingestion-plan.md), and [ADR-0001](../adr/0001-local-import-runtime.md). The parent investigation read [issue #4](https://github.com/goncalvesjoao/open-akiya/issues/4) and found no comments at review time.

## Candidate and decision

Recommend **Tsubata Town (津幡町), Ishikawa, official open-data CSV**, source key proposed as `tsubata-open-data`. Use the town's explicitly published [CSV export](https://www.town.tsubata.lg.jp/division/file/opendata/173614_empty_bank.csv), linked under 空き家バンク on its [official open-data page](https://www.town.tsubata.lg.jp/page/1773.html). This is a practical, small municipal export candidate with documented reuse permission, sale and rental rows, and explicit availability states. Coverage is the published municipal feed, not every vacant home or every offer in the selected area.

**Do not select the catalog API as the adapter transport.** Although anonymous sample API requests succeeded, the [catalog robots rules](https://catalog-data.city.kanazawa.ishikawa.jp/robots.txt) disallow `/api/`, `/datastore/`, and query URLs, and prescribe `Crawl-Delay: 10`. These rules were discovered after the three initial API probes; API probing then stopped. The town CSV is a separately published official download, not a path around an API block. The town's `/robots.txt` returned 404; absence of robots rules is not the reuse grant—the open-data page and terms are.

Sufficient to nominate a first adapter, **not sufficient to enable it or declare #4 complete**. Before pilot activation, validate identity handling and install a reviewed municipality reference with representative-point provenance. Integrated release additionally requires the bounded source pilot and the existing #3 completion gate. None of this blocks independent map/backend work using synthetic responses.

## Access, reuse, and retention

The town explicitly publishes UTF-8 comma-separated files for machine-readable reuse, including application development. Its [open-data terms](https://www.town.tsubata.lg.jp/uploaded/attachment/1311.pdf), article 1, apply **CC BY 4.0 International** unless otherwise indicated. Article 2 reserves third-party rights and does not promise they have been identified; article 4 disclaims completeness/accuracy and permits changes or removal without notice. Recheck terms at onboarding.

The [CC BY 4.0 license](https://creativecommons.org/licenses/by/4.0/) allows sharing and adaptation, including commercial use, subject to attribution, linking the license, and indicating changes. It does not clear privacy or other third-party rights. For this adapter retain only published factual CSV fields, Japanese source values needed for normalization, source ID, export URL, reviewed license, and check timestamps. This supports local storage and normalized factual display; it does not establish rights to linked PDFs, photographs, owner contacts, logos, or descriptions. Do not fetch those assets. Translation is outside this task; adaptation permission for licensed material is not a grant over third-party material.

Proposed display attribution: “出典：津幡町『空き家バンク』オープンデータ（取得日 YYYY-MM-DD、CC BY 4.0）。Open Akiya にて項目を正規化。” Link both the export/open-data page and license. No special retention period, mandatory deletion-on-feed-removal clause, or source-specific removal process was found in the reviewed town terms; this is a finding about those terms, not a claim that other rights never apply. Keep normalized factual observations under the existing local retention policy; an omitted row does not prove withdrawal. Retain provenance and license notices with any permitted reuse. Do not commit downloaded records or full payloads to the repository.

## Geography and location precision

The source scope is one municipality. Sample `全国地方公共団体コード` is `173614`; municipal name is 石川県河北郡津幡町. The published [bank page](https://www.town.tsubata.lg.jp/site/welcome/1222.html) describes the town's bank. The direct CSV offers no radius/bounding-box query. Gate its single municipal export on an independently established selected-circle/municipality intersection; do not scan other municipalities to compensate.

An official boundary candidate is [MLIT N03 administrative-area data, specification 3.1](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-N03-v3_1.html): polygons, JGD2011, municipality names, and `N03_007` administrative codes. The page lists the Ishikawa 2023 archive `N03-20230101_17_GML.zip` and warns of provisional boundaries. This is a **documented candidate reference**, not an installed/current boundary validation. Do not silently call its 2023 edition current in 2026. Pin an edition/checksum, validate the code crosswalk (`17361` administrative code versus six-digit `173614` source code), check for municipal changes, and test geographic intersection before enabling coverage. No polygon archive was collected here.

[MLIT's current terms](https://nlftp.mlit.go.jp/ksj/other/agreement.html) apply PDL 1.0 by default from 23 March 2026, require attribution and disclosure of edits, and retain individual restrictions. The N03 page also warns that Survey Act procedures may apply to secondary use; therefore **do not claim blanket clearance to redistribute boundary files**. Validate the chosen edition's supplied notices and applicable use before shipping a reference. A reviewed alternative official reference is acceptable.

Proposed municipality summary point: compute a point on surface of the reviewed Tsubata polygon, record edition, code, CRS transformation, algorithm/version, and label it as a municipality representative, never a home. This is a proposed derivation, not a verified coordinate. It can lie outside the selected circle; the summary still describes intersecting municipality candidates. Until a reviewed reference/point exists, report unsupported geographic coverage rather than inventing a center or using the town hall as a listing location.

The [CSV schema](https://catalog-data.city.kanazawa.ishikawa.jp/dataset/173614_empty_bank/resource/d6152659-e4f0-4670-a163-1742035e55ec) contains **no coordinates**. Sample addresses name a town section followed by `地内`, not an exact building. Preserve the address text, keep coordinates null, and use municipality summary grouping. Do not infer in-circle status, home distance, or an individual pin from those addresses; no geocoding is required.

## Identity and available fields

The actual town prefix confirms the same named fields as the catalog schema. Proposed source identity is `(tsubata-open-data, 全国地方公共団体コード, ID, 契約形態)`; keep sale and rental offers distinct. `ID` values are municipal strings such as `TBB000000001`. They agree between the sampled catalog and town rows, making them a concrete candidate identity. **Persistence across updates and non-reassignment are not documented or established by this single observation.** Never use catalog `_id`, row position, price, or address as stable identity: in a sampled later catalog row `_id=24` differed from the ID suffix `025`.

The sampled `URL` cells were empty. The export is a source reference shared by many offers, **not an offer-specific canonical-URL fallback**. Do not key all offers by that URL or manufacture record URLs. An adapter must use and validate municipal IDs, rejecting/quarantining blank or duplicate ambiguous IDs and suspicious identity changes; if persistence cannot be established sufficiently for the first pilot, identity remains an enablement blocker. Do not fuzzy-merge address matches. A later observed rekey must preserve prior records for review instead of silently overwriting or withdrawing them.

| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `ID`                                                                        | Candidate municipal identity; temporal guarantee remains unverified                                                                                                                                                                   |

The schema has no explicit residential-building eligibility flag. Structure text alone does not establish residential use for every row. Before accepting a listing, require affirmative source evidence of a residential building; quarantine land-only, nonresidential, blank, or ambiguous cases rather than assuming the entire export is eligible. If the permitted CSV cannot establish eligibility for any current offers, this remains an enablement blocker; linked assets are not an automatic fallback.

No free, negotiable, combined sale/rental, malformed-price, or missing-ID live sample was verified. Cover those with synthetic source-shaped fixtures; unknown prices remain null, and zero requires explicit free evidence. The current bank page offers PDFs and images, but these are outside the chosen CSV-only rights/access scope. Do not use HTML as an automatic detail fallback.

## Pagination, dates, continuation, and completeness

**CSV transport:** a single municipal file, not a paginated search. One complete, byte/record-budget-bounded response reaching valid CSV EOF can establish traversal of that export only. A prefix/range sample, truncation, oversized file, parse error, failed fetch, or unsupported geography cannot establish complete coverage. Impose a conservative maximum file size/rows before a pilot and expose budget exhaustion rather than increasing limits automatically.

For a small feed, prefer a complete bounded fetch and local processing over multi-request byte continuation. Persist processing progress against a locally retained permitted snapshot fingerprint plus parser/query version. If the body has not been fully acquired, the safe continuation is a bounded fresh request; never stitch byte offsets from changing versions. `Last-Modified` alone has not been verified as a strong snapshot identity. No source-issued durable cursor, expiry interval, snapshot isolation, or signed continuation token was found.

**Catalog technical behavior only:** the sampled API supports `limit`, `offset`, and `_id asc`, with next links. [CKAN's primary documentation](https://docs.ckan.org/en/2.9/maintaining/datastore.html#ckanext.datastore.logic.action.datastore_search) defines offset/sort/filter mechanics; it does not promise a stable versioned snapshot across changing requests. No cursor lifetime or consistency guarantee was established. These observations do not authorize the disallowed API transport and must not leak into the CSV adapter's contract.

**No verified newest-first ordering or safe date stopping.** There are no per-offer publication/modification fields in the schema. The town open-data page labels the CSV 31 July 2026, the actual file Last-Modified is 14 September, the catalog metadata is 14 September, and the human bank page has its own page update date. All are page/file/resource metadata, not offer creation or modification dates. ID order is not date order. Disable date-based early stopping and do not advance a date discovery checkpoint. Equal-date overlap cannot repair missing dates. Only a valid complete export scan can establish its own traversal coverage; never infer that older known offers are unchanged from the metadata's newest date.

Refresh stale known offers from the same permitted CSV observation, within the existing 24-hour detail-freshness/manual-refresh policies and shared job budget. A successful export may provide discovery and refresh facts without one request per row; preserve distinct per-offer successful-check outcomes. Explicit contracted status can mark unavailable. Absence, fetch failure, and an incomplete scan cannot. CSV publication may lag the human bank page: disclose source snapshot age, not instant market freshness.

## Rate policy and remaining work

No numeric request-rate or daily quota was found in reviewed town terms or export documentation. This is **unknown**, not unlimited permission. Proposed initial adapter policy: one request at a time to the town host, at least ten seconds between source requests, total request/byte/row budgets, cached export reuse, and no per-row HTTP fetching. Ten seconds is a conservative local choice for the town, not an attributed town requirement; the separate catalog actually publishes that crawl delay. Honor `Retry-After`, bounded retry/backoff and cancellation; stop on 401/403, CAPTCHA/challenge, or other access blocks. No identity rotation, proxy change, or hidden endpoint fallback.

Before enabling a first adapter, the remaining concrete checks are:

1. Implement against synthetic CSV fixtures and the established shared worker/storage contract; validate IDs and source references without claiming a temporal guarantee the source has not provided.
2. Resolve the reviewed boundary/code crosswalk/representative point and its edition-specific reuse conditions. Fail closed for unsupported geographic selection.
3. Run a small user-requested pilot when the shared map/backend gates permit: one bounded town export, full header/EOF/uniqueness check, counts and request ledger, parser quarantine evidence, repeat/cache behavior, explicit contracted offers, and location uncertainty. Verify validators only if needed; always retain bounded full-fetch fallback.
4. If municipal IDs cannot safely distinguish offers, or a current bounded export no longer contains usable offers, leave this integration disabled with that specific reason. Do not compensate by following PDF/image/detail links or the disallowed API.

The national-bank options remain unresolved. [MLIT](https://www.mlit.go.jp/totikensangyo/const/sosei_const_tk3_000131.html) identifies At Home and LIFULL as national operators; it does not license their listings. The parent rechecked [LIFULL terms](https://www.homes.co.jp/kiyaku/) articles 6 and 16: restricted reuse and commercial activities do not establish a public read-feed grant. [At Home terms](https://www.akiya-athome.jp/contents/index/?page=kiyaku) could not be re-fetched with the research browser; prior restrictions in the background note remain historical findings, not a newly verified permission decision. No paid discovery, bulk collection, source outreach, or access-block circumvention was used.
