# Desktop sample map

Run `npm install` and `npm run dev` to open Electron. Choose a center and radius, then **Import sample listings**. The worker persists fictional offers in local SQLite. Area selection, panning, zooming and reading saved listings never create an import. Saved results are initially empty and remain available after relaunch. No Supabase, Docker or credentials are required.

The renderer uses Leaflet with a geographic circle (metres), markers, drag, keyboard navigation and zoom controls. [Leaflet API reference](https://leafletjs.com/reference.html). The map uses OpenStreetMap standard raster tiles at `https://tile.openstreetmap.org/{z}/{x}/{y}.png`, with visible contributor attribution. No key is required. Follow the [OSM tile usage policy](https://operations.osmfoundation.org/policies/tiles/): no prefetching, bulk downloading or offline tile packaging. Electron identifies requests with an Open Akiya user agent. Standard HTTP caching is retained. Internet is required for tiles; tile failure displays a message while coordinate controls, imports and saved results remain usable. The app uses system fonts.

Provider URL, maximum zoom and attribution are configured in `src/renderer/src/AreaMap.tsx`. Update all three, CSP and main-process external-link validation together if switching providers. The sandboxed renderer cannot fetch source data directly. Optional [address/place search](location-search.md) runs through validated preload IPC and a configured self-hosted Nominatim provider in the utility process. Live listing sources remain disabled.

Coordinate/radius controls accept finite WGS84 coordinates and a radius greater than zero and at most 10 km. Invalid drafts retain the last accepted selection. The worker independently validates the same bounds. Filtering includes the circle boundary and shortest longitude distance across the antimeridian.

Every visible offer has its own list entry and stable identity. Coincident markers can overlap; the list keeps all offers reachable. Pin and list selection share the details view. The sample import includes a verified sale offer and two coincident unverified source-point candidates (unknown accuracy and approximate), plus an explicitly unavailable unverified offer. Unverified pins use amber dashed squares with a question mark; verified pins use round sale/rent markers. Both result rows and details label location uncertainty and explain that true distance and radius membership remain uncertain. Only verified positions display a numeric distance. Candidate inclusion uses the published source point without inventing coordinates. Municipality-only offers appear once inside expandable municipality groups. Purple rectangular summary markers display visible offer counts; their positions represent the municipality, never a listing. Groups without a documented representative point remain available through the list. Unknown-location samples appear in a separate Unknown location list when saved discovery-circle evidence intersects the selected area; they have no pins or numeric distances and share the details view. A known precise position takes precedence over discovery-circle evidence.

Show unavailable is applied before rendering results. Unknown availability remains visible. Missing results and failed queries never withdraw a saved offer. Null money is unknown; explicit zero is free. Distinct coincident sale/rent offers remain separate. Japanese source text is retained behind a details control; authored English labels describe fixtures, not real source translations.

Source links use exact-host, credential-free HTTP(S) validation and open through the system browser. Coverage remains unknown and prominently synthetic, including after a sample job succeeds. No real listings or scraped dataset are distributed. Automated Electron tests control tile requests and use temporary databases; live tiles are unnecessary for checks.

See the [desktop runtime](desktop-runtime.md) for current worker behavior and remaining acceptance requirements.

## Synthetic municipality reference evidence

These are deliberately fictional reference regions, not real Japanese administrative geography. `src/main/municipalities.ts` defines stable municipality identities and geodesic circular footprints. Intersection means the geodesic distance between the selected center and reference center is at most the sum of the two radii (boundary included). Neither listing coordinates nor the representative point determine municipality membership.

- `fixture:municipality-1`: reference circle centered at latitude 35.06, longitude 135, radius 5 km. Its representative point is the authored synthetic municipal office at latitude 35.1, longitude 135. This point is about 11.12 km from the default selected center (35, 135), outside the selected 5 km circle; the reference region still intersects that circle. The group's response retains the office/geometry provenance.
- `fixture:municipality-2`: reference circle centered at latitude 35.02, longitude 135, radius 1 km. It has no documented representative point or point provenance, so no marker is created.
- The synthetic source offer `municipality-source-point-1` publishes (35.1, 135), explicitly documented as the municipal office in `municipalitySourcePointEvidence`. The synthetic adapter converts that source evidence into the existing municipality location variant before discovery filtering and normalization; it never creates an individual house pin. Other source points retain their existing verified/unverified rules.

Unavailable offers are filtered before group IDs and counts are constructed. Returned listings include each grouped offer once for shared details; the companion list renders grouped IDs only inside their municipality. Unrecognized municipality identities have no intersection evidence and are excluded; coverage remains unknown. No real reference provider, listing geocoding or live collection is introduced.
